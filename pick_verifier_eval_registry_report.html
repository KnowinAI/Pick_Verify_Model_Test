Pick Verifier 可追溯模型评测台账方案

目的：把测试集、历史模型结果、人工标注、具体图片、粗颗粒度指标串起来，支持回归测试、对比测试和历史追溯。

1. 先说结论

你现在要解决的不是单纯“怎么做一个测试集”，而是需要一套可追溯的模型评测台账。

它需要回答：

  • 某个历史模型版本，在某个 BM 版本上，具体测了哪些样本？
  • 每个样本当时的人类标注是什么？
  • 模型当时预测了什么？原始输出是什么？
  • 准确率、召回率、漏判、误判这些数字是由哪些样本算出来的？
  • 点开某个错误桶，能不能看到具体图片？
  • 同一张样本，base、opt10、opt11 分别预测成什么？
  • 新模型相比旧模型，是哪些样本变好了，哪些样本退化了？
核心不是只保存一个 accuracy=86%，而是保存：BM 版本 + 样本清单 + 人工标注 + 模型运行记录 + 每张样本预测结果 + 指标计算明细。

2. 总体结构

建议分成四层：

1. 样本层：图片 + 人工标注
2. BM 层：某个 BM 版本包含哪些样本
3. 模型运行层：某个模型在某个 BM 上跑了一次
4. 预测结果层：这次运行中每个样本的模型输出和对错
模型结果不要覆盖写回样本表。每跑一次模型，就新增一次 run 记录和一份 predictions 明细。

3. 样本层：图片和人工标注

样本层负责回答：这张图是什么、图片在哪里、人工标准答案是什么、它有什么标签。

unknown无法判断或模型失败。

7. 粗颗粒度指标如何追溯

每个指标都必须能回到参与计算的 sample_id 列表。不要只保存 accuracy = 86%，而要能知道它的分子、分母和对应样本。

指标口径要和当前项目页面保持一致，按照“夹住 / 没夹住”分别计算精准率和召回率。

TP：真实夹住，预测夹住
FN：真实夹住，预测没夹住，也就是漏判
FP：真实没夹住，预测夹住，也就是误判
TN：真实没夹住，预测没夹住

总准确率 = (TP + TN) / 全部已计分样本
夹住精准率 = TP / (TP + FP)
夹住召回率 = TP / (TP + FN)
没夹住精准率 = TN / (TN + FN)
没夹住召回率 = TN / (TN + FP)
夹住精准率：模型判为夹住的样本里，有多少真的夹住。
夹住召回率：真实夹住的样本里，有多少被模型识别为夹住。
没夹住精准率：模型判为没夹住的样本里，有多少真的没夹住。
没夹住召回率：真实没夹住的样本里，有多少被模型识别为没夹住。

8. 推荐的查看方式

历史模型运行列表

展示 run_id、模型版本、BM版本、样本数、总准确率、夹住精准率、夹住召回率、没夹住精准率、没夹住召回率、失败数和运行时间。

单次评测详情页

展示总体指标、混淆矩阵、按物体类别/夹取关系分组指标和错误样本列表。

样本列表页

每条样本展示 cam0、cam1、人工标签、模型预测、是否正确、错误方向和关键标注。

样本详情页

展示样本图片、人工标注、所有历史模型预测结果、出现在哪些 BM 中，以及是否进入训练集。

9. 不同模型版本怎么对比

对比两个 run，例如 base on BM_v1.0 和 opt10 on BM_v1.0，可以把样本分成四类：

类型含义用途
improvedbase 错，opt10 对模型提升样本
regressedbase 对，opt10 错模型退化样本
still_wrongbase 错，opt10 也错持续失败样本
still_correctbase 对，opt10 也对稳定正确样本
准确率从 78% 到 86% 只能说明整体变好了，但不能说明哪些样本变好了、哪些样本变差了、是否牺牲了某个类别。run 对比可以回答这些问题。

10. 为什么不建议把所有模型预测都加到样本表里

短期可以在样本标注总表里加 base_pred、trained_pred、candidate_type、failure_direction 做临时分析，但长期不建议一直这么加。

  • 模型版本越来越多，表会越来越宽。
  • 同一个模型可能用不同 prompt 跑多次。
  • 同一个模型可能分别跑 BM_v1、BM_v2。
  • 很难记录原始输出、错误信息、运行耗时。
  • 很难做 run 和 run 之间的对比。
推荐结构：样本表 = 标准答案；模型结果表 = 历史答题记录。

12. 图片资产、下载、导出和导入

除了能在页面里看到图片，还需要把图片作为评测资产管理。也就是说：样本图片不仅要能展示，还要能下载、导出、导入和复现。

为什么要支持下载、导出、导入

  • 给同事复核时，需要把某一批错例图片打包发出去。
  • 训练新模型时，需要从 failure_pool 或 BM 候选池导出图片和标注。
  • 换电脑、换服务器或归档历史实验时，需要完整迁移 BM 图片和结果。
  • 历史模型评测结果必须能回到当时的具体图片，而不是只剩路径。
  • 某个指标下钻出来的一组样本，应该可以直接批量下载。

需要支持的能力

单张图片下载
单个样本 cam0/cam1 下载
某个错误桶批量下载
某个 run 的全部错例导出
某个 BM 版本完整导出
某个 BM 版本完整导入

14. 结合当前 pick-verify 项目的建议

不建议一上来大改平台。建议分三步：

  1. 先做文件级 registry：保存 BM manifest、run.json、predictions.jsonl、metrics.json。
  2. 再做评测历史查看页：查看所有历史 run、单个 run 指标、错误样本列表和 cam0/cam1 图片。
  3. 最后做模型对比页：对比 improved、regressed、still_wrong、still_correct。

15. 重要规则

规则说明
BM 样本冻结BM v1.0 冻结后，样本 ID、图片、人工标签不随便改；修正标签应生成 BM_v1.1。
模型结果只追加，不覆盖每次新增 run_id + sample_id + predicted_label，历史模型结果才不会丢。
指标从样本结果计算准确率、召回率、混淆矩阵都从 predictions.jsonl 自动计算，不手填。
指标能点回样本例如 PhoneCover 的没夹住召回率可以下钻到所有对应样本和图片。
训练集和 BM 隔离BM 不建议直接进入训练集；若发生 training_leak，需要记录或重新冻结 BM。

16. 可以对同事这样描述

我们需要的不只是一个测试集，而是一套可追溯的模型评测台账。每个 BM 版本固定一批样本和人工标签；每次模型评测都生成一个 run；run 里保存每个样本的预测结果、原始输出和对错。准确率、召回率这些指标不是孤立数字，而是可以下钻到具体样本和图片；这些图片还要能按单样本、筛选结果、错误桶、BM 版本或 run 结果进行下载、导出和导入。这样我们就能对比不同模型版本：哪些样本变好了，哪些样本退化了，哪些问题持续存在，并且历史数据可以迁移和复核。
